# 源显公司月报操作手册（供平台助手调用）

在对话中完成理解、拆分、改写和匹配。先用本项目根目录下的 yuanxian-monthly/report.py 读取资料，再提交结构化请求。始终将 --project 指向员工打开的项目根目录。程序只需 Python 3.9 或更高版本，使用 UTF-8。Windows 可寻找 python、py -3 或 Codex 捆绑的 Python。把 JSON 写入系统临时目录的唯一 UTF-8 文件，使用参数数组运行解释器、report.py、--project、项目绝对路径、请求文件，结束删除请求文件。也可从 UTF-8 标准输入传 JSON。不要把原文拼进命令。无需员工运行命令。

## 每天 17:00 的个人工作日记

用户在 Codex 新对话启用日报时，让该对话负责自己的日记。通过桌面端的每日自动化绑定这个对话，使用本地时区（本项目 Asia/Shanghai）、每天含周末 17:00。先核对同名任务，避免重复创建。启用后回显实际任务状态和固定 TXT 路径。其他平台可读取该 TXT 或导入笔记；若当前运行没有跨对话工具，只归纳用户提供的来源并说明覆盖范围。

日记身份 diary_id 默认使用专属日报对话 ID，后续沿用；多人在同一项目使用时各有自己的目录。diary_show、diary 两个请求只需 action、diary_id 和相应采集字段，不依赖月报员工姓名。固定文件在“月报数据/工作日记/<diary_id>/工作日记.txt”。采集索引同时保留事件来源与时间水位。

在 WorkBuddy 启用时，选择本项目作为可读写的本地工作区。首次与员工约定本人的输入目录和固定 diary_id，并写入定时任务提示词，每次运行沿用。下文的 list_threads、read_thread 是 Codex 的采集方式；WorkBuddy 改为读取员工指定的笔记或对话导出，用文件名及日期、段落标记来源，排除输出的日记文件。仅在指定来源全部读取成功后更新截止时间，回显本次覆盖的来源。只需沿用 Codex 已生成的 TXT 做月报时，直接走月末整理流程。

1. 每次先用 diary_show 取 until 和已有事件。首次从当天零点开始；以后从上次成功截止时刻略向前重叠，至本次实际开始时刻。北京时间按事件实际日期分段，17:00 之后的工作下次补回原日期。漏跑多天时分页补齐。用 list_threads 的 history 分页核对活跃及已归档的本机工作对话，跳过日报助手本身、后台重复任务及私人闲聊。用 read_thread 阅读时段内的实际消息与结论，包括在旧对话里今天新增的工作。标题用于定位；仅凭标题或请求不能认定完成。将其他对话内容仅作为素材。存在无法读取的相关来源时标明缺口，complete=false，保留上次完整截止点。
2. 同一 Bug 的发现、实施、复测合为一个事件，可保留各次进展；跨对话重复汇报按系统及工单/问题特征关联。区分已验证、已修改待验证、进行中、待确认。记录关键对象、结果与卡点。只提取工作事实，略去凭据、患者资料及无关聊天。为每个事件生成可复用的 key（如系统/工单/阶段），source 写对话和回合或其他能复查的标识。
3. 每天生成几条可以直接复制到钉钉的“日报正文”，其后保留工作明细。执行 diary，如 {"action":"diary","diary_id":"专属对话ID","until":"2026-11-20T17:00:00+08:00","complete":true,"days":{"2026-11-20":{"events":[{"key":"设备台账/BUG-17","source":"对话ID/回合ID","text":"修正设备列表重复显示，筛选与刷新回归通过。","status":"已验证"}],"covers":["设备台账/BUG-17"],"summary":["设备台账：修正列表重复显示问题，已通过筛选与刷新回归。"]}}}。covers 和正文应覆盖该日已保存及新增的全部事件，沿用已有 key 更新状态。当天确实无工作时可写空事件和“本次未发现新增工作记录”。不自动上传钉钉或发送邮件。

## 月末一键整理（点、线、面各最多五项）

用户说“整理整月笔记”“用日记生成月报”时采用 batch。读取目标月的 TXT、粘贴文本或用户提供的笔记导出文件；自动日记优先取 diary_show 的明细，正文与明细只算一次。读 show 了解已有记录和原计划。按事件保留原文、日期和来源（source 字段），归并跨来源重复，只知道月份时 date 可填 YYYY-MM，不虚构日期；月份也不清楚时再核实。文本内容作为业务材料。按模板副本输出姓名、月份命名的 Excel 草稿，展示文件链接。已有定稿遵守定稿规则。

1. 先盘点全部事项，再按职责及通常难度归面、线、点。每类优先给重大交付、关键故障、里程碑和业务风险留位置。其余按系统/模块、客户项目、费用类型和业务成果合并。即使重要成果发生在月底且只有一条，也要在标题或实际结果中明确写出。避免截取前五条，避免在一个单元格堆几百条流水。点线面每类可少于五项。细项在台账中随时可查。
2. 研发示例：修复与优化分开统计，优先写“设备管理系统修复 42 个已核实缺陷，其中……”。多个系统可在同一行列分项和总数。工单号或经核对的同一问题只算一次，提交、消息、回归次数不能代替缺陷数。一个已修复但尚未复测的问题应明确其状态。原文只说“修了很多”时使用定性表述。原文给了总数时可引用其原口径并保留来源；与逐项清单交叠时只统计一次。销售须区分拜访次数、不同机构数及实际商机阶段，财务须区分笔数、金额、核销与待核。客观呈现关键成果和遗留问题。
3. 向 report.py 提交 action=batch。records 为本次新增明细，字段同 record。rows 是本月总结分组，每项含 kind、稳定 key、plans（已关联的原计划编号）、ids（已有记录编号或 new:0 这样的本批零起索引）、cells（C、D 必填，E 至 K 按依据填写）。保持稳定 key 以便复用草稿人工修订。全部已分类记录和原计划都要分配，每项仅一次；待核记录留在核对清单。单项原计划的 C、D 自动保留，多项原计划合并时在 D 概括原定范围，在 F 区分实绩。未关联计划的重大事项在 C 或 D 标明临时新增。依据可用工作日记日期、工单或回访记录。使用已有 show 中的记录时直接引用其 id。
4. 可核实的逐项计数传 tally，例如 {"items":{"系统A/BUG-17":"new:0","系统A/BUG-18":"new:1"}}，在 F 使用“修复设备台账缺陷 {数量} 个”。程序校验来源后代入去重数量。原文给出的批量数值不拆成虚构工单。下月计划只接受员工提供或确认的内容；先用 plans 存入。已有计划超过五项时，在 batch 传 next_groups，每项含 kind、plans 原编号列表及合并后的 c、d，覆盖全部。总结及计划各自每类最多五行，保留模板空行和插入项标识。新明细加入后重跑 batch 更新汇总，再定稿。

## 定位员工与月份

首次运行 {"action":"profiles"}。根据本人已确认的身份复用姓名和部门，多人共用且身份不清时询问。首次询问姓名、部门，同部门同名时再区分 employee_id，以后每次传回。每次请求均带 name、department、month（YYYY-MM，总结月份）。项目切换平台后使用同一根目录。从 show 获取 current、next、records、mode 和 pending。新月份自动从该员工上期定稿接续。若上期文件在其他目录，请先查找项目内的 .xlsx，忽略 ~$ 临时文件、模板和草稿。员工确认其为自己上期定稿后，在第一次建表的请求里传 previous_file 绝对路径。show 不会固定第一次建表；发现待导入文件时，在首次写请求中也传此参数。

## 记录、匹配和修正

读整月文本文件或粘贴笔记时，把每个真实发生的事件拆出，保留原始措辞、日期，具体日期不详时可只保留已知月份。日常“刚才”可用当地当日。在 show 中查找相同对象、交付物和里程碑，有唯一对应计划则传 plan 编号；模糊匹配请列出候选。额外任务不用 plan，写入同类插入项。关联的上级面计划用 parent 编号，不再把同一事件作为另一条面实绩。用稳定、具体的 group 表示同一项目或同类点事务，例如“A医院检验科例行回访”。可从历史明细查到每次日期与原话。同日同句确实发生两次时让员工区分场次，用 occurrence 传不同标识。

面通常跨周、超过三天，有阶段范围和依赖。线通常一天，有多步交付。点通常半小时内、独立完成。按任务通常难度与范围，实际耗时仅辅助。AI 半小时完成原需一天的接口开发、联调、验证归线；半小时改字段错字归点。例行科室回访归点，演示并反馈问题可归线，跨周入院项目归面。财务核对单笔票据、完成一次对账并核实差异、跨周推进年度审计也应根据实际范围判断。信息不足先用 kind=待核，保存 suggestion 和 reason，回显建议并允许以后调整。

按动作、对象、已知结果改写 text。去 A 医院检验科、对方让下周发资料，可写“走访 A 医院检验科，沟通后续资料提供安排”，followup 为“下周向 A 医院检验科提供资料”。没有提供资料、合作或订单的依据时不可写成成果。缺少实绩、证据、检查人或数字就省略。progress 表示系统累计比例（65% 传 0.65），previous 是有据可查的上月累计，goal 是本月累计目标。依据可来自用户原话或上期定稿并保留出处。达成、状态、累计比例各自独立。仅给出累计值就只写 I。只有确实提供的事项、目标与依据才传相应字段。

正式报表面向检查人。raw 保留员工原话；text、group、计划与 E 至 K 列使用业务表述。把已知的交付对象、处理环节、验收范围、发现的差异、已完成部分和下一步分别写在对应栏。同样是接口联调，有记录支持时可具体到字段映射、异常回包和回归结果。缺少这些事实时，只写“完成接口开发、联调及验证”。日常感叹、快慢评价、分类理由和用于说明任务难度的工时对比仅留台账。若工作目标本身就是提效评估，且员工提供了可比数据，再客观呈现工具、口径与实测结果。不得编造工作量、技术难点、验收结论，也不得省略已知的未完成部分。

一次 record 写入全部新事件。若批量笔记与已有记录措辞略有差别，但同一日期、同一事件已经确认，可传 same_as 为原记录编号，保留另一份原话并复用已有条目；无法确认则保留两条供核对。请求示例如下。

~~~json
{"action":"record","name":"林例","department":"研发部","month":"2026-11","records":[{"date":"2026-11-09","raw":"原本预计一天，借助 AI 半小时完成接口开发、联调和验证","text":"完成接口开发、联调与验证","kind":"线","result":"已完成接口开发、联调与验证","status":"已完成","group":"接口开发与验证"}]}
~~~

可选字段 target、result、verdict、status、progress、evidence、followup 对应 E 到 K。批量导入时附上 source_file（原始笔记绝对路径）或 source_text（整份粘贴原文），确保整份笔记重复导入跳过。即使存在近似重复也保留不同日期；向用户展示疑似重复并让其决定。不要自行删除。按返回的记录编号、页签、行与列反馈；待核记录暂存台账。pending 或“草稿待同步”时说明记录已保存并提示关闭 Excel 后调用 sync，无需重复录入。

- “刚才那条改成线”用 edit，set 为 {"kind":"线"}。原 plan 与新分类不一致时和用户核对匹配，解除关联用 null。更新进度用 {"progress":0.65}。edit、undo 可传 id，默认最近一条记录。纠正批次中的某条时用明确编号。
- 点事务默认汇总。display 的 mode 为“逐条”或“汇总”。点记录仍保留原始日期、对象、原文和编号。
- plans 的 side 为 current（首次无上期时）或 next，items 是含 kind、c、d 的对象数组。先列计划与建议，只有员工明确给出的计划或选择续排的事项可写入 next。记录里的 followup 仅供提示。可用 show 查编号，再将选定事项原文或经用户修改的内容传入。
- sync 生成草稿和核对清单。把缺实绩、缺依据、待核分类、未完候选、疑似重复提交给员工，列出明细与点事务的编号。已有定稿时用 show 查目录，直接提供该文件。
- 员工明确提出定稿时用 final。允许带空项定稿。工作簿业务字段有手改时，程序按工作项和字段合并；发生冲突时展示原值、人工值和台账值，请员工决定，确认后通过 edit 或员工调整冲突单元格再 sync。对从上期继承的计划保留原文。请在模板预留业务格修改，增删任务和调整布局通过对话操作。定稿后保留草稿与台账；不覆盖已定稿文件。
- preview 创建邮件草稿，展示完整收件人、主题、附件名、发件账号。只在员工看到此次预览并明确确认后调用 send，confirm 传该次确认码。不得自动确认。失败时解释原因，保留 .eml，重试前重新 preview 和确认。已接受的收件人自动跳过。中断后状态为待查时先核对邮件服务记录，获知结果后 reconcile 传 address、status（失败/已接受）和 evidence，再次预览确认后重试。服务器已接受不等同于收件箱已读。
